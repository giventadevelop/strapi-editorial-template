Cloud image upload migration fix

Reference for uploading media/images to Strapi Cloud when POST /api/upload fails (HTTP 500 / invalid S3). Proven on Catholicate (June 2026): 9 distinct images linked via base64 migration endpoint.

When to use: Content and tenant links are already on Cloud, but image is missing or the frontend shows the same placeholder on every card. Say to Cursor: “Upload the Cloud images for [collection] using the Cloud image migration fix.”

How it works:

  1. Script reads local image files from public/uploads/ via DB morph table (files_related_mph).
  2. POST /api/migration/fix-published with uploadMedia (base64) — writes files on Cloud server + creates plugin::upload.file rows (provider: local).
  3. Same request links files to entries by slug + restores tenant join if missing.
  4. REST fallback (Strapi 5, June 2026): If step 3 reports Linked: N but REST populate=image still returns null, run linkImagesViaRest (scripts/lib/link-cloud-images-rest.js) — PUT each entry with the correct mediaField (image, cardImage, or pdf).

Implementation: src/index.js · scripts/push-collection-images-migration.js · scripts/lib/cloud-image-migration-config.js · scripts/lib/link-cloud-images-rest.js

After every Strapi Cloud deploy: Images for collections fixed via the migration workaround may show broken in admin and API until you re-run finish:collection-images-on-cloud (or the batch command below). Deploy replaces the Cloud app container; public/uploads/ on disk is ephemeral. Database rows and image.url paths remain, but the binary files are gone.

Why Bishops / Dioceses / Parishes stay OK

Those directory types were seeded earlier (often with working upload or S3-backed URLs). Front-end-imported types (Catholicate, Holy Synod, Training, Institutions, etc.) use the migration base64 fix because Cloud POST /api/upload fails when S3 is misconfigured. That fix stores files as provider: local on the Cloud server filesystem — which is wiped on redeploy.

Permanent prevention: Configure valid AWS_* on Strapi Cloud and set UPLOAD_PROVIDER=aws-s3 so new uploads land in S3 (strapi-editorial-media/prod/). Until then, treat finish:*-on-cloud as part of every production deploy checklist.

1. Prerequisites

  1. Phase A local import done (images in public/uploads/).
  2. Phase B content push done: npm run push:<section>-to-cloud -- --tenant-id=tenant_demo_002.
  3. .env: STRAPI_CLOUD_URL, STRAPI_CLOUD_API_TOKEN (Full Access).
  4. Migration code deployed on Cloud (git push origin main or npx strapi deploy --force).
  5. Stop local Strapi dev server before running image scripts.
Shell env override: If STRAPI_CLOUD_URL is set to http://localhost:1337 in your terminal, scripts use dotenv override: true to read Cloud URL from .env.

2. One-command fix (any registered collection)

Finish images on Cloud
npm run finish:collection-images-on-cloud -- --collection=catholicate --tenant-id=tenant_demo_002

5. REST fallback (when morph link fails verification)

Symptom: Finish script prints Created: N | Linked: N but verification shows 0 distinct images | N missing (exit code 1).
Cause: Migration endpoint inserts into files_related_mph but Strapi 5 REST does not expose the relation.
Fix: scripts/lib/link-cloud-images-rest.js — PUT /api/{plural}/{documentId} with { data: { [mediaField]: fileId } }. Pass the correct mediaField from cloud-image-migration-config.js.

6. REST verification

GET {STRAPI_CLOUD_URL}/api/{rest-plural}?pagination[pageSize]=100&populate[0]=image&populate[1]=tenant&filters[tenant][tenantId][$eq]=tenant_demo_002&sort=order:asc

Each entry should have a distinct image.url (e.g. /uploads/Catholicos_1_….jpeg). Count of unique URLs should match entry count (shared category images may repeat for Institutions).
