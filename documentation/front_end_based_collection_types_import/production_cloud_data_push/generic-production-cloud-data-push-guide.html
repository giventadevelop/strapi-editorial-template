Production / Strapi Cloud data push – Generic guide

How directory collection types move from local Strapi (after mosc-temp import) to Strapi Cloud production, with tenant integrity and safe upserts.

Strapi project root: C:\project_workspace\strapi-editorial-template

Production (Cloud): STRAPI_CLOUD_URL in .env (e.g. https://awesome-birthday-82f0a4fa96.strapiapp.com)

Tenant: tenant_demo_002 (always filter and link by tenant on push)

Bulk tenant port: Tenant Clone & Cloud Port Runbook — clone to new tenant ID, then npm run push:tenant-to-cloud

Canonical example script: scripts/push-catholicate-to-cloud.js · npm: push:catholicate-to-cloud

2. Script types in this repo

ScriptPurposeUse for directory CMS types?
push-catholicate-to-cloud.js Read one collection from embedded local Strapi; upsert to Cloud REST API; upload images from public/uploads; resolve/create tenant. Yes – template for slug+tenant directory entries (clone per type).

import-*-from-mosc-temp.js Phase A only (not cloud). Run before cloud push.

3. Reuse vs separate push scripts

There is no single generic push script for all directory types yet. Use this decision table:

Schema patternPush scriptAction
name, slug, excerpt, body, image, order, tenant
(Catholicate, Ecumenical, Saints, Publications)		 Clone push-catholicate-to-cloud.js Change 3 constants: UID, PLURAL, log labels. Same upsert key: slug + tenantId. Same image upload block.
Standard fields + subtitle, location, established, address, email, phones, website
(Theological Seminaries)		 push-theological-seminaries-to-cloud.js Clone catholicate script; extend payload with extra attributes.
Standard fields + memberType, address, email, phones
(Holy Synod)		 push-holy-synod-to-cloud.js Clone catholicate script; include memberType enum in payload.
Unique upsert key (e.g. liturgy date) Custom script Follow push-liturgy-days-to-cloud.js pattern instead.

3.1 What to change when cloning the Catholicate script

  1. Copy scripts/push-catholicate-to-cloud.js → scripts/push-<section>-to-cloud.js
  2. Set UID (e.g. api::saint-entry.saint-entry) and PLURAL (e.g. saint-entries)
  3. Rename helper getCloudCatholicateKeys → getCloudEntryKeys (same logic)
  4. Adjust payload to match schema (see per-type PRD)
  5. Add "push:<section>-to-cloud": "node ./scripts/push-<section>-to-cloud.js" to package.json
  6. Optional: add scripts/verify-<section>-cloud.js (copy _tmp-verify-cloud-catholicate.js)

5. Tenant integrity

  • Always pass --tenant-id=tenant_demo_002 when pushing MOSC redesign content.
  • Local read filters by tenant relation; cloud upsert index is ${slug}_${tenantId}.
  • If tenant missing on Cloud, script creates it from local tenant row (name, tenantId, domain, description).
  • Every entry payload includes tenant: <cloudTenantDocumentId>.
  • Verify with REST: filters[tenant][tenantId][$eq]=tenant_demo_002 and populate[0]=tenant.

6. Standard push flow (per collection type)

  1. Ensure phase A local import completed (local import PRD).
  2. Stop local Strapi dev server (embedded Strapi in push script needs DB lock).
  3. Dry run: set DRY_RUN=1&& node scripts/push-<section>-to-cloud.js --tenant-id=tenant_demo_002
  4. Push: node scripts/push-<section>-to-cloud.js --tenant-id=tenant_demo_002
  5. Verify in Cloud Content Manager + REST (see per-type PRD).
  6. If images failed on Cloud: use Cloud image upload migration fix (§ below) — not only --images-only.

6. Cloud image upload fix (when /api/upload fails)

Proven fix (June 2026): Base64 upload via POST /api/migration/fix-published bypasses broken Cloud S3. Catholicate: 9/9 distinct images linked.

Full reference: cloud-image-upload-migration-fix.html · Cursor rule: .cursor/rules/strapi-cloud-production-durable-s3-image-upload-not-ephemeral-uploads.mdc

Finish images for any registered collection
npm run finish:collection-images-on-cloud -- --collection=catholicate --tenant-id=tenant_demo_002

Replace catholicate with: ecumenical, saints, publications, theological-seminaries, holy-synod, institutions, training. Each per-type PRD has § Cloud image upload fix and a copy-paste AI prompt.

Order: (1) push content push:<section>-to-cloud → (2) deploy migration code if needed → (3) finish:collection-images-on-cloud.

Prompt template (customize [SECTION], [UID], [PLURAL])
