PRD: Tenant Replication & Multi-Tenant Editor Access

Product Requirements Document — Defines requirements, constraints, and effort estimates for two related capabilities in the Strapi editorial template:

  1. Tenant replication — Copy all content scoped to tenant_demo_002 to a new tenant in one operation.
  2. Multi-tenant editors — Allow a single admin user (editor) to be associated with more than one tenantId.

Status: Implemented (Phase 1 + Phase 2) · Reference tenant: tenant_demo_002 · Strapi version: 5.x

2. Goals & Non-Goals

🎯 Goals
  • Document a repeatable path to duplicate an entire tenant’s CMS content (starting from tenant_demo_002).
  • Clarify schema, relation, slug, media, and single-type blockers before implementation.
  • Define requirements for editors who manage content across multiple tenants.
  • Provide effort estimates and phased delivery options for stakeholders.
🚫 Non-Goals (this PRD)
  • Implementing the clone script or schema changes (analysis and requirements only).
  • Changing frontend Next.js apps — frontends already filter by filters[tenant][tenantId][$eq]=....
  • Duplicating global types (category, author, homepage, global) unless explicitly scoped in a later phase.
  • Cross-instance migration to a brand-new Strapi Cloud project (covered as an alternative, not primary scope).

4. Epic 1: Replicate tenant_demo_002 to a New Tenant

4.1 User story

As a Super Admin,
I want to clone all CMS content from tenant_demo_002 to a new tenant (e.g. tenant_demo_003) in one operation,
So that a new site/brand can launch with the same structure and content without manual re-import per collection.

4.2 Feasibility: one-shot clone

Not available today. A new script (proposed name: clone-tenant-records.js) must be built. Strapi export/import and existing push scripts do not filter by source tenant for a full clone.

4.3 Technical requirements for clone

Functional requirements
  1. Accept --source-tenant-id and --target-tenant-id (target must exist or be created with --create-target).
  2. Process content types in dependency order (see §4.4).
  3. Maintain oldDocumentId → newDocumentId map per UID; rewrite internal relations using the map.
  4. Set tenant on every cloned row to the target tenant (Document Service + join tables).
  5. Handle draft & publish for articles: copy draft and published rows; ensure tenant links on both (see publish middleware in src/bootstrap.js).
  6. Handle media: option to reuse same S3 files (recommended) or duplicate upload records.
  7. Support --dry-run (counts only) and --types=articles,dioceses (subset).
  8. Emit summary report: created/skipped/failed per type.

4.4 Clone dependency order

Based on rest_api_push_to_cloud.js Phase 1 ordering and internal relation graph:

1. tenants (create target if --create-target)
2. dioceses
3. parishes, priests, bishops (diocesan/retired/catholicos), directory-entries
4. institutions, church-dignitaries, committees, spiritual-organisations, pilgrim-centres, seminaries
5. holy-synod-members, ecumenical-articles, saint-entries, catholicate-entries
6. theological-seminaries, training-programs, publication-entries
7. kalpana-editions → kalpana-documents
8. liturgy-days
9. flash-news-items, advertisement-slots
10. articles (last among editorial — references global category/author)
11. directory-home, kalpana-page (single types — see blocker)

4.5 Blockers & decisions

BlockerImpactDecision required
Global slug uniqueness UID slug fields are unique per content type across the whole instance, not per tenant. Cloning without suffix/prefix will fail on duplicate slugs. Suffix strategy: {slug}-{targetTenantSuffix} or prefix with tenant slug.
Single types (directory-home, kalpana-page) Strapi allows only one document per single type per locale. Cannot have separate Directory Home per tenant on same instance. Convert to collection type, OR skip clone for single types, OR use separate Strapi instance per tenant.
Shared categories/authors Cloned articles keep pointing at existing global categories/authors. Accept shared taxonomy OR add tenant to category/author (schema change).
Media relations Strapi 5 Document Service may reject media connect on create. Use files_related_mph pattern from data_import_seed_directory_mosc_in.js.
Volume Liturgy days + directory entries may be thousands of rows. Batch creates, progress logging, resumable checkpoints.

4.6 Alternative approaches

ApproachProsConsEffort
A. Custom clone script (same instance) One command; stays on current Cloud project Slug + single-type constraints 5–10 days
B. New Strapi instance Clean slugs; no collision with source tenant Second Cloud project, DNS, env setup 3–7 days
C. Manual per-type scripts Reuse existing push-* patterns Not one-shot; easy to miss types 3–5 days + high error risk
D. Super Admin duplicate in CM No code Not scalable for hundreds/thousands of entries Not viable
Recommendation: Choose Approach A if the new tenant must live on the same Strapi Cloud project as tenant_demo_002. Resolve single-type and slug strategy in a design review before coding. Choose Approach B if the new tenant is effectively a separate product/site.

5. Epic 2: One User → Multiple Tenants

5.1 User story

As a Super Admin,
I want one editor account to manage content for multiple tenants (e.g. tenant_demo_002 and directory_mosc_001),
So that the same person does not need separate login credentials per site.

5.2 Current constraint

adminUserEmail on Editor Tenant Assignment is unique. Assignment logic in src/utils/tenant-assignment.js and src/bootstrap.js resolves exactly one tenant per email. Documented in .cursor/rules/multi-tenant-assignment.mdc as many-to-one (user → tenant).

5.3 Requirements for multi-tenant editors

Schema & data model
  • Allow multiple editor-tenant rows per email OR replace with many-to-many join (email ↔ tenant).
  • Remove or relax unique: true on adminUserEmail; add composite unique on (adminUserEmail, tenant) if using collection rows.
Runtime behavior
  • Active tenant context — Editor session must track which tenant is “active” for list/create operations.
  • Content Manager — Tenant switcher in admin UI; lists and create forms scoped to active tenant.
  • Document middleware — Filter findMany by active tenant (not all assigned tenants unless merged view is explicitly requested).
  • Lifecycles — beforeCreate assigns tenant from active context, not first mapping found.
  • Mutations — Block update/delete/publish when document tenant ≠ active tenant.
Scripts & ops
  • Extend assign-editor-to-directory-tenant.js to add a tenant without replacing existing assignment.
  • New script: list/remove tenant assignments per email.
  • Update grant scripts and verify scripts for multi-tenant cases.

5.4 Workaround (no code change)

Supported today: Create two Strapi admin users (e.g. editor.news@example.com → tenant_demo_002, editor.directory@example.com → directory_mosc_001). Same person can use two browsers or profiles. Effort: ~30 minutes per editor.

5.5 UX options for implementation

OptionEditor seesComplexity
1. Tenant switcher (recommended)One tenant at a time; explicit switch in admin headerMedium–high
2. Merged listAll assigned tenants’ content in one list (with tenant column)Medium; create still ambiguous
3. Separate accountsOne tenant per loginNone (current)

7. Recommended Implementation Phases

Phase 0 — Discovery (before build)
  1. Run tenant inventory for tenant_demo_002 on local and Cloud.
  2. Stakeholder decision: same instance vs new instance; single-type strategy; slug suffix rule.
  3. Stakeholder decision: multi-tenant editor — switcher vs separate accounts.
Phase 1 — Tenant clone MVP
  1. Implement clone-tenant-records.js with dependency order and ID map.
  2. Test on local SQLite with small subset (--types=flash-news-items).
  3. Full dry-run against production API (read-only token).
  4. Execute clone to target tenant; verify with existing verify-* scripts.
Phase 2 — Multi-tenant editors (if approved)
  1. Schema migration for editor ↔ tenant many-to-many.
  2. Backend: active tenant context + middleware + lifecycle updates.
  3. Admin UI: tenant switcher.
  4. Migration: existing single assignments remain valid.
