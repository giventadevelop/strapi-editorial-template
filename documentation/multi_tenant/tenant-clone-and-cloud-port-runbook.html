Runbook: Tenant Clone & Cloud Port

Purpose: Operational guide for copying all content from an existing tenant (e.g. tenant_demo_002) to a new tenant ID on the same local Strapi instance, then pushing that tenant’s data and media to Strapi Cloud.

Case study (June 2026): tenant_demo_002 → mosc_malankara_orthodox_2 (slug suffix -mo2) · ~3,022 local records · 3,018 created on Cloud · 302 image/PDF links via REST fallback.

Related PRD: Tenant Replication & Multi-Tenant Editor Access · Image fix: Cloud image upload migration fix

1. End-to-end overview

PhaseWhereGoalPrimary script / npm
A Local clone Local SQLite Strapi Copy all collection-type rows from source tenant → target tenant; suffix slugs globally clone-tenant-records.js · npm run clone:tenant
B Cloud content Strapi Cloud REST API Upsert all target-tenant records to Cloud (media stripped from payload) push-tenant-to-cloud.js · npm run push:tenant-to-cloud
C Cloud media Cloud migration + REST Upload binaries from public/uploads/ and link to entries finish:all-collection-images-on-cloud + REST fallback (see §6–7)
D Editors Local + Cloud Assign editor to new tenant; grant CM permissions on Cloud assign-editor-to-directory-tenant.js · grant:editor-directory-on-cloud
Slugs are global per Strapi instance. A cloned tenant on the same instance (local or Cloud) must use a slug suffix (e.g. -mo2) so rows do not collide with the source tenant. The clone and push scripts support --slug-suffix (local) or inherit suffixed slugs from the local DB (cloud push).

3. Phase A — Local tenant clone

Step-by-step
  1. Inventory source tenant (optional): npm run inventory:tenant -- --tenant-id=tenant_demo_002
  2. Dry-run clone: see command block below
  3. Execute clone (create target tenant if needed): add --create-target
  4. Inventory target tenant — expect same row counts minus known edge-case failures
Inventory target tenant
npm run inventory:tenant -- --tenant-id=mosc_malankara_orthodox_2
Clone (dry-run)
node scripts/clone-tenant-records.js --source-tenant-id=tenant_demo_002 --target-tenant-id=mosc_malankara_orthodox_2 --create-target --slug-suffix=-mo2 --dry-run
Clone (execute) — stop Strapi first
node scripts/clone-tenant-records.js --source-tenant-id=tenant_demo_002 --target-tenant-id=mosc_malankara_orthodox_2 --create-target --slug-suffix=-mo2
Re-clone from scratch (destructive on target)
node scripts/clone-tenant-records.js --source-tenant-id=tenant_demo_002 --target-tenant-id=mosc_malankara_orthodox_2 --slug-suffix=-mo2 --clean-target --force
Skipped on clone: Single types directory-home and kalpana-page (max one per Strapi instance). Kalpana page content remains on the source tenant unless manually copied.

4. Phase B — Cloud deploy & content push

Step-by-step
  1. Deploy schema/code to Cloud: npx strapi login → npm run deploy
  2. Create target tenant on Cloud (API or admin) if it does not exist
  3. Dry-run push from local DB
  4. Full push (~18 min for ~3k records)
  5. Compare inventories (local vs Cloud) — see §9
Probe Cloud tenants
$env:NODE_TLS_REJECT_UNAUTHORIZED='0'; node scripts/probe-cloud-tenants.js --full --tenant-id=mosc_malankara_orthodox_2
Push tenant to Cloud (dry-run)
$env:NODE_TLS_REJECT_UNAUTHORIZED='0'; node scripts/push-tenant-to-cloud.js --tenant-id=mosc_malankara_orthodox_2 --dry-run
Push tenant to Cloud (full)
$env:NODE_TLS_REJECT_UNAUTHORIZED='0'; node scripts/push-tenant-to-cloud.js --tenant-id=mosc_malankara_orthodox_2 --delay-ms=80
Re-push skipped articles only (force)
$env:NODE_TLS_REJECT_UNAUTHORIZED='0'; npm run push:tenant-to-cloud -- --tenant-id=mosc_malankara_orthodox_2 --types=articles --force
Case study result: Created 3,018 · Skipped 4 (article slugs already on Cloud) · Failed 0. Local total 3,022 = 3,018 + 4 skipped.

5. Phase C — Cloud media (images & PDFs)

Content push does not upload media. After Phase B, run the image migration pipeline. See also Cloud image upload migration fix.

Finish all collection images (set tenant env!)
$env:NODE_TLS_REJECT_UNAUTHORIZED='0'; $env:TENANT_ID='mosc_malankara_orthodox_2'; npm run finish:all-collection-images-on-cloud -- --tenant-id=mosc_malankara_orthodox_2
Known failure mode: finish:all-collection-images-on-cloud may exit 1 with “Created: N | Linked: N” but verification shows all MISSING. The migration endpoint’s DB morph link does not surface via Strapi 5 REST. Use the REST fallback in §7.2.
REST link fallback (all registered collections)
Uses scripts/lib/link-cloud-images-rest.js with correct mediaField per collection (see cloud-image-migration-config.js). After fix (June 2026), linkImagesViaRest accepts mediaField: image | cardImage | pdf.

6. Phase D — Editor assignment & permissions

Assign editor locally (multi-tenant — add mode)
node scripts/assign-editor-to-directory-tenant.js giventauser@gmail.com mosc_malankara_orthodox_2 --add
Grant directory CM permissions on Cloud
$env:NODE_TLS_REJECT_UNAUTHORIZED='0'; npm run grant:editor-directory-on-cloud
Assign editor on Cloud (REST)
POST /api/editor-tenants with { adminUserEmail, assignmentKey: "email__tenantId", tenant: tenantDocumentId }

Editor must log out and back in to see the tenant switcher and new content types.

8. Kalpana-specific issues (editions + documents)

Why Kalpana is different

Kalpana uses non-standard media field names and PDF binaries, not the usual image field used by directory card types.

Content typeMedia fieldRegistry keyNotes
kalpana-edition cardImage (thumbnail) kalpana-editions 12 edition rows per tenant; linked via migration + REST
kalpana-document pdf (not image) kalpana-documents ~350 PDFs per tenant; larger payloads; dedicated push script available
kalpana-page single type — Not cloned per tenant on same instance — manual or separate instance

8.1 Kalpana issue: REST link used wrong field name

Symptom: HTTP 400 ValidationError: Invalid key image when linking kalpana-editions or kalpana-documents.
Cause: linkImagesViaRest hardcoded { image: fileId } in PUT body.
Fix (June 2026): Pass mediaField from cloud-image-migration-config.js — cardImage for editions, pdf for documents. Updated in scripts/lib/link-cloud-images-rest.js and push-collection-images-migration.js.

8.3 Kalpana commands

Per-type image finish (editions)
$env:NODE_TLS_REJECT_UNAUTHORIZED='0'; $env:TENANT_ID='mosc_malankara_orthodox_2'; npm run finish:collection-images-on-cloud -- --collection=kalpana-editions --tenant-id=mosc_malankara_orthodox_2
Per-type PDF finish (documents)
$env:NODE_TLS_REJECT_UNAUTHORIZED='0'; $env:TENANT_ID='mosc_malankara_orthodox_2'; npm run finish:kalpana-documents-on-cloud -- --tenant-id=mosc_malankara_orthodox_2
Full Kalpana push (legacy per-type — content + PDF upload)
$env:NODE_TLS_REJECT_UNAUTHORIZED='0'; npm run push:kalpana-documents-to-cloud -- --tenant-id=mosc_malankara_orthodox_2
PDFs only retry (after content exists on Cloud)
$env:NODE_TLS_REJECT_UNAUTHORIZED='0'; node scripts/push-kalpana-documents-to-cloud.js --tenant-id=mosc_malankara_orthodox_2 --pdfs-only
When to use bulk vs per-type Kalpana scripts: After push:tenant-to-cloud, kalpana records are already on Cloud. You only need media linking (Phase C). Use finish:kalpana-documents-on-cloud or REST fallback — not a full re-import — unless PDF files were never uploaded.
Full Kalpana guide: kalpana-import-and-cloud-push.html
